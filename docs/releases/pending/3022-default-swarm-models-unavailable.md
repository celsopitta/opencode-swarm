# Default swarm models rotated onto the verified zen keyless roster; model-unavailable fallback now fires (issue #3022)

## What changed

- **Default models rotated (all hosts).** `opencode/minimax-m2.5-free` (coder) and `opencode/gpt-5-nano` (test_engineer, critic_\*, curator_\*, and every fallback chain) were dropped from the opencode zen keyless roster — fresh installs failed at first delegation with `Model unavailable: <id>` and zero fallback advances. Defaults now use roster-verified ids: coder `opencode/nemotron-3-ultra-free`, cheap tier `opencode/mimo-v2.6-flash-free`, everything else `opencode/big-pickle` (unchanged). Verified live 2026-10-02 on OpenCode 2.0.21 (`opencode run -m` matrix).
- **Roster guard.** `tests/fixtures/opencode-zen-keyless-roster.json` snapshots the 8 live-verified keyless ids (with the refresh procedure in `_meta`); `tests/unit/config/default-models-roster-guard.test.ts` fails when any default or fallback leaves the roster, and `src/config/project-init.ts` now derives its example fallback chain from `DEFAULT_AGENT_CONFIGS` instead of a hardcoded duplicate. `tests/unit/config/multilevel-fallback.test.ts` was rewritten to import the real constants (its local copy had drifted into fiction).
- **`Model unavailable` classifies retryable-with-fallback.** `classifyProviderFailure` now routes `Model unavailable: <id>` / `ModelUnavailableError` (OpenCode v2 `SessionRunnerModel.ModelUnavailableError`, provider code `provider.no-route`) to `provider.unavailable` / `retry_fallback` — advancing to the next `fallback_models` entry instead of dropping the error as `provider.unknown`/`do_not_retry`. The transient pattern gains `model.?unavailable`; the guardrails tool-output advisory is unaffected (its provider-marker pre-filter carries no model vocabulary — pinned by negative controls).
- **OpenCode v2 fallback advance works end to end.** The v2 event mapper accepts both error-event dialects (`session.execution.failed` with a `data` payload — the live plugin stream — and the SDK's `session.error`/`properties`) and maps `session.status` type-preserving so live `busy`/`retry` transitions can never terminalize a running session. The pump seeds session identity from `session.created`/`session.agent.selected` (`data.agent`) into the same map the v1 chat boundary writes, unblocking the no-route advance arm. The advanced model is applied on v2 by re-invoking the host's `ctx.agent.transform` surface and rewriting the registered agent's `model` reference (`src/host/v2/model-apply.ts`, keyed on the exact registered name — no phantom bare-role agents on multi-swarm configs; no-op on v1).
- **v2 startup model preflight.** v2 hosts carry no OpencodeClient, so the catalog-backed preflight was silent there. Setup now runs the pure `collectModelRosterWarnings` (new in `src/services/model-preflight.ts`) against the checked-in verified roster — inline at the setup tail, withTimeout-bounded and fail-open (live probing showed the v2 plugin realm never runs post-setup timers, so a deferred schedule would silently never fire) — and surfaces one bounded warning per off-roster opencode-zen configured model at startup instead of failing at first delegation.

## Upgrade notes

- If you pinned `agents.*.model` or `fallback_models` to `opencode/minimax-m2.5-free` / `opencode/gpt-5-nano` in your `opencode-swarm.json`, rotate them to a roster-verified id (the startup preflight will name them). Historical release notes still mention the retired ids — they describe the roster as it was.
